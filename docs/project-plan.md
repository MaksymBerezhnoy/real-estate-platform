# Pet-проект: платформа недвижимости на WordPress

Стек и план реализации.

## Коротко

Каталог недвижимости на продажу на WordPress как инженерной платформе: Bedrock, плагин на Composer с PSR-4, Gutenberg-блоки, REST-поиск, CI с линтерами и тестами. Проект идёт в три этапа:

| Этап | Что входит | Срок при полном дне |
| --- | --- | --- |
| 1. MVP | Каталог, поиск с фильтрами, страница объекта, главная, правдоподобные данные и замеры, тесты, CI, README | 5 недель и 1 день подготовки |
| 2. Карта и AI-поиск | Поиск по нарисованной области на карте, поиск запросом своими словами | 6-7 дней |
| 3. Multisite | Сеть сайтов агентств и агрегатор на главном сайте | 3-5 дней |

Всего около 7-7,5 недель. Каждый этап заканчивается рабочим состоянием, поэтому остановиться можно после любого.

## Что строим

**Этап 1. MVP (один сайт):**

- каталог объектов на продажу с типом недвижимости (квартира, дом), городом и районом;
- классический поиск с фильтрами по цене, площади, числу комнат, типу и району;
- четыре страницы: главная, каталог, страница объекта, служебная страница индекса в админке;
- 4 блока: поиск, карточка объекта, сетка объектов с фильтрами, ипотечный калькулятор;
- два языка интерфейса и контента: украинский и английский.

**Этап 2. Карта и AI-поиск:**

- страница «Поиск на карте»: пользователь рисует область, список и метки показывают только объекты внутри неё;
- второй режим поиска: запрос своими словами превращается в фильтры каталога;
- переключатель «Классический / AI» в блоке поиска.

**Этап 3. Multisite:**

- у каждого агентства свой сайт, плагин и тема общие;
- главный сайт - агрегатор с поиском по объектам всей сети через общую индексную таблицу.

**Не входит в проект:** аренда, личные кабинеты, заявки, избранное, оплата. Всё это - строка в roadmap в README. Стресс-тест «до отказа» тоже не делаем: в CI идёт короткий нагрузочный тест как защита от регрессий, а полные замеры описаны в разделе «Правдоподобие данных и замеров».

## Дизайн

Прототип четырёх экранов: [Прототип: платформа недвижимости](https://claude.ai/artifact/CQ5uyeJ35Pv1YQgvkoLAFN). Он задаёт внешний вид и поведение, вёрстка в теме делается по нему.

| Экран | Что на нём |
| --- | --- |
| Главная | Фото города с блоком поиска, быстрые ссылки на районы, «Новые объекты», «Районы», «Агентства сети», плашка про калькулятор |
| Каталог | Горизонтальная панель фильтров, сетка карточек по четыре в ряд, сортировка, пагинация, кнопка «Поиск на карте» |
| Страница объекта | Мозаика галереи, карточка с ценой и агентством, ключевые параметры, описание, характеристики, калькулятор, похожие объекты |
| Поиск на карте | Карта с метками цен, рисование области, список объектов внутри неё |

**Дизайн-система в `theme.json`.** Все блоки берут значения только из неё, через CSS-переменные WordPress.

- Цвета: фирменный зелёный `#087A4D`, тёмно-синий для текста и футера `#0F1B2D`, вторичный текст `#4B5868`, линии `#E3E8EE`, светлый фон `#F5F7FA`, жёлтая метка `#FFD768`.
- Шрифты: Manrope для заголовков и цен, Inter для текста. Подключаются локально через `fontFace` в `theme.json`, без запросов к Google Fonts.
- Шкала отступов и скруглений задаётся там же.

**Карточка объекта** - главный повторяющийся элемент: фото, метки «Новое» и «Цена снижена», счётчик фото, цена и цена за м², число комнат, площадь и этаж с иконками, адрес, агентство, давность публикации.

**Фотографии.** Нужен набор из 150-200 снимков со свободной лицензией, разложенный по типам помещений. Генератор собирает из него галерею каждого объекта. В наборе 151 снимок с Pexels: фасады многоэтажек (в основном Киев и Восточная Европа) - 25, частные дома - 24 (13 американских и 11 европейских), гостиные - 30, кухни - 24, спальни - 24, ванные - 20, панорамы города - 4, из них три киевские. Лицензия у всех Pexels License, авторы и страницы-источники перечислены в `data/README.md`.

Сами файлы в Git не хранятся: папка `data/photos/` в `.gitignore`. В репозитории лежат манифест `data/photos.json` (имя файла, тип помещения, источник, автор, лицензия, контрольная сумма), команда загрузки набора по манифесту и файл с источниками. Так клон остаётся лёгким, а чужие снимки не раздаются отдельным набором. Для тестов в CI используются несколько собственных изображений-заглушек.

**Модель данных:**

- CPT `mbre_property` с `show_in_rest`, адрес страницы объекта - `/property/...`;
- таксономии: тип недвижимости, местоположение (иерархическая: город и район);
- мета: цена, площадь, число комнат, этаж, широта и долгота - через `register_post_meta` с типами и `show_in_rest`, ключи вида `mbre_price`;
- индексная таблица поиска: одна строка на объект с числовыми полями, языком записи и индексами, синхронизация по хукам `save_post` и `deleted_post`. Она заменяет `meta_query` в поиске.

Координаты входят в модель уже в MVP, хотя карта появляется на этапе 2: добавить два поля сразу дешевле, чем потом мигрировать 10 тысяч объектов.

**Имена и префиксы.** Префикс `mbre` ставится только на то, что живёт в общем пространстве WordPress. Внутри namespace `MB\RealEstate` классы и функции пишутся без префикса. Префикс `mb_` не используется: так начинаются встроенные функции PHP для многобайтовых строк.

| Что | Имя |
| --- | --- |
| CPT | `mbre_property` |
| Мета-ключи | `mbre_price`, `mbre_area` и так далее |
| REST namespace | `mbre/v1` |
| Индексная таблица | `{$wpdb->prefix}mbre_property_index` |
| Блоки | `mbre/property-card`, `mbre/property-grid` и так далее |
| Хуки и опции | `mbre_index_rebuilt`, `mbre_settings` |
| PHP namespace | `MB\RealEstate` |
| Плагин и тема | `mb-real-estate`, `mb-real-estate-theme` |

Имена фиксируются до первого коммита: ключ CPT и мета-ключи записываются в базу, и переименование потом означает миграцию данных.

**Хранение: мета плюс индекс.** Мета остаётся источником истины: с ней работают редактор, REST, ревизии и Polylang. Индексная таблица - производная копия для поиска, её всегда можно собрать заново. Рассматривались ещё два варианта: всё на кастомных таблицах (теряются редактор, шаблоны и список в админке) и CPT с числовыми полями только в своей таблице (нет дублирования, но свой код чтения и записи). Это решение описывается в README.

**Пересборка индекса.** Логика живёт в одном сервис-классе, который обрабатывает объекты пачками по 200-500. У него две точки входа: WP-CLI команда и страница «Инструменты - Индекс объектов» в админке. Страница показывает число объектов, число строк в индексе и дату последней пересборки, а пересборку запускает запросами к REST endpoint с прогресс-баром. Генератор данных остаётся только в WP-CLI.

**Генератор данных.** Требования к нему вынесены в раздел «Правдоподобие данных и замеров».

**Поиск по области (этап 2).** В индексную таблицу добавляется колонка с точкой и пространственным индексом. Запрос получает вершины полигона, сначала отсекает объекты по описывающему прямоугольнику, затем проверяет попадание в полигон средствами MySQL. Число вершин и площадь области ограничены в схеме аргументов endpoint.

**AI-поиск (этап 2).** Модель не ищет объекты сама: она только переводит текст в те же параметры, что принимает endpoint классического поиска.

- Запрос уходит на свой REST endpoint, тот обращается к API модели с сервера. Ключ лежит в `.env` и в браузер не попадает.
- Ответ модели проверяется по той же схеме аргументов, что и обычный поиск. Всё, что схему не прошло, отбрасывается.
- Пользователь видит распознанные фильтры метками и может поправить их в каталоге.
- Защита: ограничение частоты запросов с одного адреса, кеш одинаковых запросов, лимит длины текста.
- При ошибке или недоступности API включается классический поиск.
- В тестах ответ модели подменяется, CI к внешнему API не обращается.

Провайдер модели пока не выбран. Это решение принимается в начале этапа 2 и записывается в README.

## Правдоподобие данных и замеров

Цель - чтобы за каждую цифру в README можно было ответить. Абсолютной гарантии скорости проект не даёт: он показывает, как система ведёт себя на данных и нагрузке, максимально похожих на настоящие, и честно называет границы этого сходства.

### Генератор данных

| Что | Как делается | Зачем |
| --- | --- | --- |
| Распределения | Районы с неравными весами; цена считается как площадь на цену метра в районе с разбросом; площадь зависит от числа комнат; этаж не выше этажности дома | Фильтры отсекают разные доли данных, как в жизни, и индексы работают в реальных условиях |
| Адреса и координаты | Справочник реальных улиц по районам из OpenStreetMap; точка ставится внутри границы района и не попадает в воду | Карта и поиск по области выглядят и нагружаются правдоподобно |
| Тексты | 300-500 заранее написанных описаний на двух языках лежат в репозитории как справочник и подбираются под тип и параметры объекта | Текстовый поиск работает не по десятку шаблонов |
| Фото | У каждого объекта галерея из 8-15 снимков по типам помещений и свои записи вложений, которые ссылаются на общие файлы | База вырастает до реального размера (сотни тысяч вложений), диск не раздувается |
| История | Даты публикации размазаны на два года; часть объектов продана или в черновиках; у части есть прежняя цена для метки «Цена снижена» | Сортировка по дате, статусы и метки работают на осмысленных данных |
| Агентства | Несколько крупных и много мелких | Перекос нужен для этапа 3 |
| Переводы | У каждого объекта есть английская версия | Число записей удваивается, индекс учитывает язык |
| Воспроизводимость | Фиксированное зерно случайности и параметр объёма | Замер можно повторить и получить те же данные |

Справочники улиц и границ районов берутся из OpenStreetMap с указанием авторства. Настоящие объявления с порталов недвижимости не собираются: это нарушает их условия использования и затрагивает персональные данные.

### Объём

Замеры идут на трёх объёмах: 10, 50 и 100 тысяч объектов. В README попадает график времени ответа от объёма для `meta_query` и для индексной таблицы: он показывает не одну удачную цифру, а то, как решения масштабируются.

### Нагрузка

| Что | Как делается |
| --- | --- |
| Смесь запросов | Около 70% - поиск в каталоге, 20% - страницы объектов, по 5% - главная и поиск по области |
| Параметры | Фильтры выбираются случайно из большого набора с весами: популярные сочетания чаще, редкие реже |
| Кеш | Холодный и прогретый кеш измеряются отдельно |
| Запись во время чтения | Фоновый сценарий сохраняет объекты, пока идёт поиск: проверяется синхронизация индекса под нагрузкой |
| Паузы | Между действиями виртуального пользователя есть паузы, как у человека |

### Среда

- **CI на раннере GitHub:** короткий тест с порогами, только как защита от регрессий. Абсолютным цифрам оттуда верить нельзя.
- **Локальная машина:** сравнение «до и после» на трёх объёмах.
- **Недорогой VPS:** один прогон на сервере, похожем на продакшен (nginx, PHP-FPM, MySQL, Redis). Даёт цифры, которые можно называть без оговорок про железо. Стоит несколько долларов и полдня; сервер после прогона удаляется.

### Чего это всё равно не покажет

Реальные всплески трафика и ботов, влияние сторонних плагинов, медиатеку с уникальными файлами на диске. Эти ограничения перечисляются в README в разделе «Методика замеров».

## Git-процесс

- Ветки от `main`: `feature/...`, `fix/...`, `chore/...`.
- Один PR - одна задача на 100-300 строк.
- Коммиты с префиксом в верхнем регистре: `FEAT:`, `FIX:`, `REFACTOR:`, `CHORE:`.
- Описание PR: что сделано, зачем, как проверить.
- Слияние только при зелёных проверках, через squash merge.
- Перед слиянием - самопроверка diff и комментарии к спорным местам.
